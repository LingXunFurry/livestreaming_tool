# Codex 开发总任务书 V2：凌巽的酒馆直播间装修系统

## 0. 项目定位与最高优先级规则

你将作为本项目的技术负责人、前端工程师、视觉实现工程师和本地运行环境工程师，开发一套完整、可迁移、可维护的本地 Web 直播间装修系统。

**项目名称：凌巽的酒馆（Lingxun's Tavern Overlay）**

这不是普通的网站、静态直播背景，也不是单一平台的弹幕插件，而是一套面向 B 站和抖音双平台直播的、具有原创像素 RPG 酒馆风格的本地 Web 应用。

本项目有六条最高优先级要求：

1. **规范先行**：所有用户确认的要求必须写入仓库规范文件，不能只依赖聊天上下文。
2. **阶段验收**：严格执行 Checkpoint，未经用户明确确认不得进入下一阶段。
3. **双平台并行**：B 站和抖音的直播页面必须能够同时运行，不能互斥切换。
4. **统一服务管理**：必须实现一键启动、统一停止、状态检查、日志和跨设备迁移。
5. **模块化美术制作**：允许 AI 生成独立透明底像素素材，再进行离线组合；禁止直接生成整张直播背景，也不能主要依赖 CSS/SVG 模拟场景插画。
6. **尊重现有素材版权**：用户提供的角色稿件、兽装照片和角色像素图默认不使用，不允许擅自修改、重绘或图生图。

任何功能、架构或视觉实现均不能违反以上要求。

# 二、产品功能需求

## 2.1 总体目标

建立一套以“凌巽的酒馆”为主题的直播间装修系统。

主要视觉方向：

**克制的复古像素 RPG × 温暖的幻想酒馆 × 风元素冒险世界**

设计目标：

- 像精心制作的独立像素游戏。
- 有明显的个人风格。
- 降低 AI 绘画感。
- 不喧宾夺主。
- 游戏内容始终是画面的重点。
- 可以由用户在后台灵活控制。

## 2.2 双平台网页

第一阶段仅开发 1920×1080 横屏。

必须提供：

```text
/live/bilibili
/live/douyin
/admin
```

对应本地 URL 示例：

```text
http://127.0.0.1:3000/live/bilibili
http://127.0.0.1:3000/live/douyin
http://127.0.0.1:3000/admin
```

B 站和抖音页面必须能同时打开。

两者共享视觉组件、基础场景、歌词服务和全局直播信息，但保留独立的平台组件和设置。

不能通过一个互斥的“当前直播平台”变量来决定哪个页面存在。

## 2.3 实际直播方式

项目本身不负责 RTMP 推流编码。

B 站直播姬、抖音直播伴侣分别加载各自的网页素材源。

游戏画面、麦克风和系统声音由直播软件分别捕获。

网页主要提供透明的直播装修层。

游戏窗口区域需要能保持透明，允许底层游戏捕获源透出。

禁止将 OBS 设置为必需依赖。

直播客户端对本地 URL 网页源的兼容性必须实际验证，不能提前标注为已通过。

# 三、统一启动与服务管理系统

**这一章是 V2 新增的核心要求，必须完整写入 `RUNTIME.md` 和 `OPERATIONS.md`。**

## 3.1 基本原则

整个直播间系统必须可以通过单一入口启动。

用户不能被要求每次直播都手动运行：

```text
npm run frontend
npm run backend
npm run websocket
npm run lyrics
```

也不能依赖用户记住多个端口和多个终端命令。

前端、后端、状态同步和内部适配器的生命周期应由统一入口管理。

优先采用一个本地 Web 服务统一托管：

- 前端静态资源
- B 站直播页面
- 抖音直播页面
- 管理后台
- WebSocket 服务
- 内部状态管理
- 平台数据适配器

只有技术上确实必要时，才启动额外子进程。

## 3.2 Windows 优先

用户主要在 Windows 上直播。

项目必须提供至少以下三个入口：

```text
启动直播间.bat
关闭直播间.bat
检查运行状态.bat
```

可以同时提供英文名称作为兼容入口：

```text
start.bat
stop.bat
status.bat
```

Windows 脚本可以调用 PowerShell 或 Node.js，但必须保持统一入口。

脚本必须支持：

- 从任意当前工作目录启动。
- 路径中包含中文。
- 路径中包含空格。
- 不依赖固定用户名。
- 不依赖固定盘符。
- 不依赖项目只能放在 C 盘。
- 不需要管理员权限执行日常启动。
- 避免因终端关闭造成意外的服务中断。

如果需要 Python，Windows 命令优先使用 `py` 或项目自己的解释器，不得假设 `python` 命令一定可用。

但本项目优先考虑 Node.js，不应无故同时引入两套运行环境。

## 3.3 启动行为

用户运行：

```text
启动直播间.bat
```

程序应该：

1. 自动定位项目目录。
2. 检查必需的运行环境。
3. 检查程序文件是否完整。
4. 检查配置是否存在。
5. 检查端口是否可用。
6. 判断是否已有同一项目实例正在运行。
7. 启动必要的本地服务。
8. 等待本地健康检查通过。
9. 打印直播页面和管理后台 URL。
10. 可配置是否自动打开管理后台浏览器。

启动成功后，应输出类似：

```text
======================================
 Lingxun's Tavern Overlay
======================================

System: RUNNING
Local Service: http://127.0.0.1:3000

Bilibili Overlay:
http://127.0.0.1:3000/live/bilibili

Douyin Overlay:
http://127.0.0.1:3000/live/douyin

Admin Dashboard:
http://127.0.0.1:3000/admin

Music Adapter: DISCONNECTED
Bilibili Events: NOT CONFIGURED

Logs: ./data/logs/

======================================
```

以上是期望输出格式，不得在实际服务未启动时伪造成功状态。

歌词与 B 站接口尚未配置时，系统仍应该正常启动，并在管理后台清楚显示该组件尚未连接。

## 3.4 关闭服务

运行：

```text
关闭直播间.bat
```

应当：

- 识别属于当前项目的服务进程。
- 正常关闭 WebSocket。
- 停止内部任务。
- 保存允许持久化的状态。
- 释放端口。
- 清理自身进程信息。
- 不终止无关 Node.js 进程。

不得通过模糊匹配执行强制关闭所有 `node.exe` 等危险操作。

如果存在外部网易云状态服务，只能在其确实属于本项目管理的子进程时自动停止，不得关闭用户自行运行的第三方程序。

## 3.5 运行状态检查

运行：

```text
检查运行状态.bat
```

能够显示：

- 主服务是否启动。
- 实际监听端口。
- 服务版本。
- 服务启动时间。
- B 站页面是否可访问。
- 抖音页面是否可访问。
- 管理后台是否可访问。
- WebSocket 是否正常。
- 网易云适配器是否连接。
- B 站事件适配器是否连接。

应区分：

- `RUNNING`
- `STOPPED`
- `DEGRADED`
- `ERROR`

例如网易云未启动，不代表整个直播系统已经崩溃，应标记为部分功能不可用。

## 3.6 健康检查接口

本地 Web 服务至少提供：

```text
GET /health
GET /api/runtime/status
```

`/health` 用于基础就绪检查。

`/api/runtime/status` 用于返回各组件状态。

状态接口应当提供机器可读的 JSON，并避免暴露敏感凭证。

后台页面应有简单的“系统状态”视图。

## 3.7 单实例与端口冲突

用户重复运行启动脚本时，不应该启动多个冲突实例。

如果同一个项目已经运行，应提示现有服务地址。

如果端口被其他程序占用，应该报告：

- 当前尝试使用的端口。
- 端口不可用的原因。
- 可执行的解决方案。

不得直接结束不属于本项目的程序。

端口必须可配置。

如果采用备用端口，实际输出的所有 URL 必须与新端口一致。

## 3.8 日志与错误处理

建立：

```text
data/logs/
```

至少记录：

- 启动时间
- 关闭时间
- 关键异常
- WebSocket 连接问题
- 外部适配器连接失败
- 服务崩溃或异常退出

日志应控制大小，避免长期直播导致日志无限增长。

不得把 B 站或其他服务的访问令牌、Cookie、密码等敏感信息写入日志。

任何外部服务故障都不能导致整个网页系统直接退出。

例如网易云服务断开，应只导致歌词组件进入不可用状态，而不是把两个直播页面一起关闭。

## 3.9 本地访问安全

服务默认只监听：

```text
127.0.0.1
```

不默认向公网开放。

不要为了方便接入浏览器源而直接监听所有网络接口。

管理后台涉及配置修改，未来如需要局域网管理，必须另外设计身份验证和访问控制。

# 四、跨电脑迁移与便携运行

**本章必须写入 `MIGRATION.md`，并纳入正式验收。**

## 4.1 可迁移性是正式产品需求

项目未来可能从当前 Windows 电脑迁移到另一台 Windows 直播电脑。

不得把当前机器的绝对路径、用户名、播放器位置或网络环境硬编码进业务逻辑。

禁止出现只能在开发电脑上运行的实现。

## 4.2 统一目录结构

建议使用类似结构：

```text
lingxun-tavern/
├── start.bat
├── stop.bat
├── status.bat
├── package.json
├── package-lock.json
├── AGENTS.md
├── README.md
│
├── apps/
│   ├── web/
│   └── server/
│
├── packages/
│   └── shared/
│
├── scripts/
│
├── assets/
│   ├── generated/
│   ├── backgrounds/
│   ├── ui/
│   └── user-originals/
│
├── config/
│   └── example.json
│
├── data/
│   ├── settings.json
│   ├── logs/
│   └── backups/
│
└── docs/
```

具体目录可以在 CP0 根据技术栈适当调整，但要保持以下边界：

- 程序代码与用户配置分开。
- 原始美术素材与生成结果分开。
- 用户数据与临时构建文件分开。
- 生成日志不能污染源码。
- 迁移时应能够明确识别需要保留的数据。

## 4.3 迁移内容

迁移后应尽量保留：

- UI 配色和配置
- 场景设置
- 歌词开关
- 平台专属设置
- 今日委托及公告模板
- 用户确认的美术素材
- 布局配置
- 其他需要持久化的数据

不得把机器相关的临时状态作为必要迁移条件。

例如：

- 旧电脑进程 PID
- 旧电脑绝对路径
- 旧电脑端口占用信息
- 旧电脑临时缓存

这些应该由新电脑重新生成。

## 4.4 统一配置

配置应由同一个模块负责读取、校验和保存。

禁止多个组件各自硬编码配置路径。

优先使用相对路径或明确的数据目录配置。

例如：

```text
config/example.json
data/settings.json
```

敏感凭证与普通设置分离。

不得把真实 API 凭证提交进 Git 仓库。

配置写入要防止意外中断造成文件损坏，并提供必要的备份或恢复方式。

## 4.5 两种迁移方式

需要在文档中明确区分：

**A. 开发版迁移**

把项目复制到另一台电脑。

安装项目要求的 Node.js 版本。

执行一次依赖安装或初始化。

随后使用统一启动脚本运行。

**B. 未来便携发行版**

作为后续交付目标，支持将构建产物、必要资源与运行环境打包，减少新电脑手动安装的步骤。

首期不必强行制作 Windows 安装程序，但必须避免架构阻碍未来制作便携版。

不得把仅有源码、仍需大量手动配置的开发版宣传成真正免安装的便携发行版。

## 4.6 迁移验收

最终必须验证：

1. 在一个新的目录中复制项目。
2. 不依赖原来的绝对路径。
3. 按文档初始化。
4. 通过统一启动入口启动。
5. 两个直播页面都可访问。
6. 管理后台能读取持久化配置。
7. 已确认的素材正常显示。
8. 用户修改能够正确保存。
9. 未连接的外部平台有明确状态提示。
10. 不依赖旧电脑的缓存才能启动。

# 五、视觉设计系统

本章必须完整记录在 `DESIGN_SYSTEM.md`。

## 5.1 主题定位

整体主题为：

**凌巽的酒馆 × 冒险者公会 × 复古像素 RPG**

不追求宏大、豪华、写实的幻想酒馆。

目标是具有个人特色、简洁、温暖的像素游戏界面。

应该像经过人工设计的独立游戏 UI，而不是随机拼凑的直播素材。

## 5.2 固定配色

| 颜色 | HEX | 用途 |
|---|---|---|
| 深海军蓝 | `#1E2B45` | 主背景 |
| 夜幕蓝 | `#142238` | 深背景及阴影 |
| 雾蓝灰 | `#7083A0` | 边框 |
| 石板蓝 | `#364E6A` | 次级面板 |
| 奶油白 | `#F3ECDD` | 主要文字 |
| 暖金色 | `#C9A85E` | 标题、强调 |
| 龙角红 | `#D24943` | LIVE、警示 |
| 淡风蓝 | `#A8C7D1` | 风元素 |
| 深木棕 | `#5A3E2B` | 木质结构 |
| 浅木棕 | `#8A6547` | 木质高光 |

以上为设计系统初始固定 Token。

未经用户确认，不得随意更改主题颜色。

整体以深蓝与中性色为主，金色、红色和风蓝只作适量强调。

## 5.3 风格约束

必须避免：

- AI 风格的华丽场景。
- 大面积浮雕金边。
- 模糊的材质边缘。
- 厚涂和写实灯光。
- 过量魔法粒子。
- 复杂光效。
- 装饰元素堆砌。
- 过于圆润的现代卡片。
- 无意义的渐变和光晕。
- 不一致的透视与像素比例。

优先使用：

- 有限色板。
- 清楚的像素边缘。
- 统一的像素尺度。
- 简洁的 RPG 菜单窗口。
- 少量木质酒馆元素。
- 有节制的风元素标识。
- 明确的信息层级。
- 充足的留白。

## 5.4 布局原则

游戏区域永远是主要视觉内容。

顶部标题栏和底部状态栏保持轻量。

右侧保留功能区。

游戏画面不得强制拉伸。

不应为了装饰而显著压缩实际游戏可视区域。

第一版不需要大幅常驻角色插画。

# 六、AI 生图与素材制作政策

本章必须完整记录在 `ASSET_POLICY.md`。

## 6.1 允许模块化 AI 生图

用户允许生成原创的、彼此独立的像素美术素材。

例如：

- 透明底酒杯
- 透明底木桌
- 透明底蜡烛
- 透明底酒瓶
- 透明底书架
- 透明底柜台
- 透明底提灯
- 透明底魔法书
- 透明底公会任务板
- 透明底风元素装饰

每个素材必须具有单独的文件和明确用途。

## 6.2 禁止一键生成完整背景

不能直接生成一张包含所有酒馆装饰、游戏区和弹幕框的 1920×1080 AI 背景。

必须按以下流程制作：

```text
布局设计
   ↓
确定所需独立素材
   ↓
逐件生成透明背景素材
   ↓
检查素材质量
   ↓
统一像素尺度与色彩
   ↓
用户验收素材
   ↓
离线拼接背景
   ↓
添加真正的网页功能组件
```

未经素材阶段确认，不允许大规模生成。

## 6.3 不允许用复杂前端绘图替代美术素材

不要主要用大量 CSS、div、SVG 路径或 Canvas 手绘代码来制作酒馆家具、蜡烛、酒杯和复杂背景插画。

这些应该使用经过确认的独立美术资产。

但 CSS 仍应正常负责：

- 网页布局
- 文本
- 简单边框
- 按钮
- 组件尺寸
- 状态变化
- 显示与隐藏
- 基础交互

SVG 可以用于简单几何图标和功能性 UI。

## 6.4 素材质量要求

优先使用真正透明的 PNG。

禁止伪透明棋盘格背景。

必须统一：

- 像素密度
- 描边粗细
- 光照方向
- 透视
- 色板
- 美术风格

对于不符合风格要求的素材，重新生成或暂时弃用，不要勉强拼入场景。

## 6.5 素材清单

建立：

```text
assets/manifest.json
```

记录素材名称、路径、来源、生成方式、版本、是否经过用户确认和使用位置。

## 6.6 用户现有角色图片

第一阶段默认不使用。

未经用户明确许可，不允许：

- AI 重绘
- 图生图
- 改变颜色
- 裁切角色
- 抠图
- 局部补全
- 修改外观
- 融入新的 AI 场景
- 擅自制作衍生形象

如用户未来允许放入某张现有图片，应完整、等比例、原样展示，并遵循其授权范围。

## 9.1 所有 Checkpoint 的通用规则

1. 重新阅读规范文件。

4. 运行实际测试。
5. 提供截图和预览地址。
6. 提供修改文件列表。
7. 创建 Git Commit。
8. 更新状态为 `WAITING_USER_REVIEW`。

```text
NOT_STARTED
IN_PROGRESS
WAITING_USER_REVIEW
NEEDS_REVISION
APPROVED
BLOCKED
```

不得自行把当前阶段改为 `APPROVED`。

用户未明确批准前，不得开始下一阶段。
